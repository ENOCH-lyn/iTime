# iTime 需求访谈问题清单

版本：0.1；日期：2026-10-02；状态：待用户逐轮回答。

## 回答与记录方式

问题中的举例用于帮助表达需求，不是默认选项。每轮可回答一个主题，也可按编号答复。暂时不清楚时可写“给我推荐方案”“后续再定”或“首发不做”，不强求一次回答全部。

同一问题有几个紧密相关的子项时可分别回答。回答后记录：用户原意、明确决定、首发/后续范围、影响需求编号、仍待澄清项。发生变更时保留旧决定及替代原因。

当前已确认：仓库名 iTime；Web/App 完整用户功能及 UI；Web 管理后台；注册登录、服务端同步及 AI；后台配置 AI 端点/Key；项目内 GitHub 凭据；以详细访谈完善 PRD。以下仅追问未决定的细节。

| 编号 | 具体问题 | 为什么需要确认 |
| --- | --- | --- |

| A02 | 首要服务大学生，还是也面向职场、自由职业、考研等人群？哪类用户最优先？ | 决定是否以“课表”作为主入口 |
| A03 | 主要使用地区是中国大陆、海外还是两者？首发语言及后续语言是什么？ | 影响登录、AI、部署、支付和时区 |
| A04 | 用户用了第一天后，你最希望解决的一个问题是什么？最应突出的三个价值是什么？ | 避免功能齐全但主价值不清 |
| A05 | “完整功能”是要求首个正式版双端全部一致，还是允许内测按模块逐步补齐，正式版再一致？ | 区分研发顺序与交付缩水 |

| A08 | 如果收费，希望订阅、买断、按 AI 用量付费还是组合？免费用户有哪些完整可用能力？ | 决定权益和额度模型 |
| A09 | 预计试用时长、每日/月额度、会员档位和心理价位是多少？会员到期后历史数据还能如何使用？ | 定义持续访问与履约 |

| A11 | 用户是否可以共同规划、分享任务或协作？还是所有任务始终属于个人？ | 影响数据隔离和同步复杂度 |
| A12 | 有无偏好的竞品或你讨厌的交互？希望继承什么、避免什么？ | 建立产品和设计参照 |

| F05 | 哪些是偏好：上午不深思、晚上运动、每日学习上限、周末休息？偏好冲突谁优先？ | 区分硬约束与软建议 |
| F06 | 希望排满空闲时间，还是保留可配置的自由时间和每日任务上限？ | 避免计划过载 |

| F08 | 简单任务需要几步？复杂任务允许多少步？操作链条可以由用户提供或用模板吗？ | 不应机械强制3—5步 |
| F09 | AI缺少关键信息时先提问，还是给出带假设的草稿？哪些假设必须显式展示？ | 防止生成虚构章节、资料或进度 |
| F10 | 任务总时长超出空闲时间时，按什么排序取舍？是否展示未安排原因和替代方案？ | 不能通过违反硬约束凑满计划 |
| F11 | AI结果直接保存，还是先预览、局部接受/拒绝、确认后应用？ | 决定用户控制权与幂等性 |
| F12 | 支持拖拽、改时间、改步骤、拆段、合并、锁定、撤销/重做到什么范围？ | 手工纠错是完整规划的重要部分 |
| F13 | 临时来任务或执行超时时，自动重排、提示重排还是纯手动？已开始/已完成部分能否动？ | 保护执行事实 |
| F14 | “重新生成”只改未锁定部分还是全日重算？保留多少历史版本、是否可恢复？ | 防止覆盖用户劳动 |
| F15 | 是否展示“为何这样安排”和备选方案？用户能用对话修改局部计划吗？ | 影响可解释性和交互 |
| F16 | 服务不可用或额度耗尽时，能否手动排期？是否需要不依赖AI的规则排期？ | 定义产品在故障中的可用性 |
| F17 | 新用户没有历史效率数据时如何初始化偏好？用户能查看、更正和重置学习结果吗？ | 冷启动与长期个性化 |
| F18 | 一天的归属在午夜切换还是用户可设凌晨几点？旅行更换时区时未来计划按当地时间还是原时区？ | 日期和跨日规则影响全部模块 |
