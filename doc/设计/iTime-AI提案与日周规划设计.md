# iTime AI 提案与日周规划设计

版本：0.1；更新：2026-10-03。本文细化 `REQ-CHAT-02`、`REQ-PLAN-01`、`REQ-PLAN-02`，定义 Web 首版可预览 AI 规划提案、确认应用、周计划版本和手工纠错合同。本文中的密度、可规划时段、提案有效期和首版交互粒度是用户授权代理自行决定后的可演进工程默认，不表述为用户原始决定。

## 1. 范围与方案选择

本阶段交付：

- 通用 `Proposal / ProposalChange` 提案内核，首个变更类型为日/周计划。
- 独立 `planning` AI 能力配置、持久化作业、逐尝试成本、用户额度和治理日志。
- 用户从规划页或全局对话明确选择“生成计划”，输入单日/整周、日期、任务、密度、缓冲和可规划时段。
- 模型正文与结构化提案分离；结构化内容通过唯一工具调用返回，服务端确定性校验后才成为可预览提案。
- 提案整体确认或拒绝；确认后生成不可变周计划版本。重复确认至多应用一次。
- 已确认计划的时间、任务步骤和日内顺序可手工纠错；每次保存生成新的不可变周版本。
- 独立 `/plans` 页面查看生成状态、提案差异、估计、未排项、冲突和历史版本；已确认计划块投影到统一日历。

本阶段不交付：

- 锁定单块、局部接受、拆合段、任意历史版本恢复和多步撤销/重做。
- 无 AI 时自动生成规则计划。
- 自动修改固定日历、任务完成状态、执行事实、任务估时或长期偏好。
- 将模型正文或客户端拼装 JSON 直接写入正式计划。

比较过三种实现：

1. **独立规划能力 + 通用提案 + 不可变周版本（采用）**：规划使用独立配置和结构化工具输出，确认时统一复核；边界清晰，可复用已有作业、额度和治理链路。
2. 把 JSON 混入普通对话正文：改动少，但正文流、结构校验、重试和用户可见内容相互污染，无法可靠证明“文字不等于可应用结构”。
3. 纯本地规则排期：确定性强，但不满足 AI 规划、自然语言补充和估计说明；可在后续作为 AI 故障降级，不替代本阶段。

## 2. 核心不变量

1. 规划使用用户时区的真实日历日期和当地午夜边界，不使用 04:00 活动日切换边界。
2. 模型只能引用服务端输入快照中的任务、任务实例和步骤；不能创建未知 ID、移动固定安排或修改任务事实。
3. 生成时和确认时均校验计划块。无效结构不会创建提案，也不会结算用户额度。
4. 提案结果通过校验并可查看时结算额度。之后拒绝、自然过期或因输入变化失效不退款。
5. 确认时锁定账号规划输入修订号。任务、步骤、任务日期、实例状态、时区、固定日历或当前计划发生变化时，旧提案不能应用。
6. 同一自然周只有一个当前计划版本。单日规划只替换该日计划块，保留同周其他日期；整周规划替换完整自然周。
7. 计划块与固定占用、其他计划块采用半开区间 `[start, end)`；端点相邻不算重叠，但必须满足配置的缓冲。
8. 已确认版本不可原地修改。AI 应用和手工纠错都创建新版本，旧版本用于追溯。
9. 计划块不代表任务完成，也不改变步骤完成状态。后续执行事实独立保存。
10. 所有写操作继续使用全账号 `operation_id` 幂等合同；未知保存状态可用原操作重试。

## 3. 数据模型

### 3.1 PlanningInputRevision

每个用户一行：

- `owner_id`
- 单调递增 `revision`
- `updated_at`

数据库触发器在规划相关源表发生插入、更新或删除时递增修订号。首批覆盖：

- `user_time_settings`
- `tasks`、`task_steps`、`task_schedules`、`task_occurrence_states`
- `calendar_series`、`calendar_exceptions`、`calendar_additions`
- 订阅主事件、覆盖和 detached event
- `plans` 当前版本切换

生成快照时对修订行加共享锁；确认和手工保存时加排他锁。触发器与该锁形成顺序，避免多条 `READ COMMITTED` 查询混入不同提交，也避免“确认复核结束后、提交前”插入新固定安排的竞态。

### 3.2 PlanningInputSnapshot

不可变快照保存：

- `id`、`owner_id`、`revision`
- 请求范围：`scope=day|week`、目标日期、自然周起止、用户时区
- `density=loose|balanced|tight`、缓冲分钟、每日可规划起止时刻
- 用户说明、选中任务 ID
- 规范化任务候选、完整有序步骤、截止和拆分参数
- 范围内固定 occurrence 及来源版本
- 当前周计划 ID/版本和需要保留的日期
- 规范化 SHA-256、创建时间

快照正文只进入必要的 AI 请求和 7 天技术正文日志，不复制平台 Key 或鉴权头。快照长期保留最小可审计字段；任务正文等输入按后续账号删除和数据生命周期统一清理。

### 3.3 Proposal / ProposalChange

`Proposal` 保存：

- `id`、`owner_id`、`kind=plan`
- `source_job_id`、可选 `conversation_id` 和消息 ID
- `input_snapshot_id`、`schema_version`
- `status=pending|applied|rejected`
- 标题、摘要、假设、警告、规范化 payload
- `expires_at`、`applied_at`、`rejected_at`
- `applied_plan_id`、`applied_plan_version_id`
- `version`、创建/更新时间

提案默认 7 天可确认。API 通过时间、输入修订号和当前周计划版本计算 `effective_status=pending|applied|rejected|expired|conflicted`，避免只依赖过期清理任务才显示真实状态。

`ProposalChange` 按顺序保存可展示差异：

- `action=create|update|delete`
- `entity_type=plan|scheduled_block`
- 可选目标 ID
- `before_data`、`after_data`
- `position`

首版只允许整体确认或整体拒绝。后续局部接受可在保持提案不变的前提下增加选择记录，不改变当前数据合同。

### 3.4 Plan / PlanVersion

`Plan` 是用户某个自然周的稳定聚合：

- `id`、`owner_id`、`week_start_date`
- `time_zone`
- `current_version_id`
- 单调递增 `version`
- 创建/更新时间

同一用户和周起始日唯一。用户时区后续变化不改写已有周计划时区。

`PlanVersion` 是完整且不可变的周快照：

- `id`、`plan_id`、`owner_id`、`version`
- `source=ai|manual`
- 可选 `proposal_id`
- `scope=day|week`、目标日期
- 密度、缓冲、每日可规划起止时刻
- 摘要、假设、输入修订号
- 创建时间

`ScheduledBlock` 保存：

- `plan_version_id`、`owner_id`
- `position`
- `task_id`、可选 `occurrence_key`
- 任务标题快照、步骤 ID 和步骤标题快照
- 当地日期/时刻、时区、UTC 起止
- `estimate_source=user|ai` 和该候选采用的总估时

`PlanUnscheduledItem` 保存未排或部分未排事实：

- 任务、可选 occurrence、剩余分钟
- 原因 `no_capacity|deadline_conflict|fixed_conflict|missing_estimate|outside_scope`
- 对用户可见的简短说明

## 4. 规划输入和工程默认

日计划范围为目标当地日期；周计划按周一至周日。目标日期最多允许当前日期前 31 天至后 366 天，避免无界生成。

默认值：

| 项目 | 默认与范围 |
| --- | --- |
| 密度 | `balanced` |
| 缓冲 | 15 分钟；允许 0—60 分钟，5 分钟步进 |
| 可规划时段 | 当地 08:00—22:00；用户每次生成可改 |
| 时间粒度 | 15 分钟 |
| 单日任务块上限 | 宽松 240 分钟、均衡 360 分钟、紧凑 480 分钟 |
| 单次块上限 | 180 分钟 |
| 提案有效期 | 7 天 |
| 单次候选 | 最多 100 个任务候选、100 个计划块 |

这些值是可演进工程默认，不等同睡眠、用餐或通勤偏好。用户自定义固定不可安排时间继续是硬约束。后续偏好模块可以提供每天不同的可规划时段；首版每次请求使用同一日内窗口。

未指定任务时，读取最多 100 个活动、未完成任务：

- 无截止任务形成一个候选。
- 非重复任务形成一个候选，保留日期型或定时截止。
- 重复任务按范围展开开放 occurrence，每个 occurrence 是独立候选。
- 已完成、已跳过、归档、回收站和已清理任务不进入候选。
- 超过上限时拒绝自动全选并要求用户缩小任务范围，不静默截断。

用户可提交任务 ID 过滤；对重复任务，该任务在范围内的开放 occurrence 一并进入。没有候选时不调用供应商、不预留额度，页面展示空状态并允许返回任务页。

## 5. 模型输入、输出和校验

`planning` 配置必须通过合成工具调用测试后才能发布。请求使用一次 OpenAI 兼容 chat completion：

- 普通可见正文用于简短说明。
- 唯一命名工具 `submit_itime_plan` 承载结构化参数。
- `tool_choice` 固定为该工具；不允许多个、未知或缺失工具调用。
- 工具参数流在 worker 内有界聚合，不写入正文 SSE。
- 工具 schema、参数和正文都计入 usage 缺失时的估算。

结构化参数包含：

- 摘要和有限条假设。
- 无用户估时任务的估计分钟与理由。
- 计划块：候选 key、当地日期、开始/结束时刻、步骤 ID。
- 未排项：候选 key、剩余分钟、枚举原因和说明。

服务端在创建提案前校验：

1. JSON/schema、数量、文本和总大小限制。
2. 所有候选、任务和步骤属于快照且未重复越权引用。
3. 当地时间可在冻结时区中严格解析；夏令时缺失或重复时刻不能静默移动。
4. 块位于请求日期和可规划时段内，15 分钟对齐，时长为正且不超过 180 分钟。
5. 与 `busy=true`、`status=scheduled`、UTC 区间有效的固定 occurrence 不重叠，并满足缓冲；取消、来源取消和空闲安排不占用。
6. 计划块之间不重叠并满足缓冲。
7. 块结束不晚于任务截止；日期型截止使用任务时区当地日末。
8. 不可拆任务只能有一个完整块；每块满足最小连续时长。
9. 每个候选的已排分钟加未排分钟等于采用估时；不能超排或漏项。
10. 每日总任务分钟不超过密度上限。

校验失败走作业失败合同，不创建提案、不结算用户额度。网络和限流可在总截止时间内有界重试；确定性结构或业务校验失败不重复消耗同一配置。

## 6. 接单、完成和额度事务

生成入口接受：

- `operation_id`
- 可选 `conversation_id` 和 `expected_conversation_version`
- `scope`、`target_date`
- 密度、缓冲、可规划时段
- 选中任务 ID 和自然语言说明

接单事务：

1. 鉴权、AI 访问状态和参数校验。
2. 锁定规划输入修订行并创建一致输入快照。
3. 检查同一会话最多一个活动作业、账号所有用户额度 AI 作业合计最多 3 个。
4. 读取已发布 `planning` 配置和价格，生成冻结请求体与预留估算。
5. 可选地写入对话用户消息、assistant 占位消息和生成映射。
6. 写入作业、规划生成映射、初始事件、额度预留和操作去重结果。

worker 成功事务：

1. 以租约和作业状态锁定唯一运行尝试。
2. 校验结构化结果并写 `Proposal / ProposalChange`。
3. 完成 provider attempt 与成本，执行 `settle_success()`。
4. 更新可选 assistant 消息、作业输出和终态事件。
5. 复核质检开关并创建样本。

任一步失败整体回滚。失败、超时、取消释放预留；晚到输出不能创建提案或扣额。提案拒绝和过期不修改已结算账本。

## 7. 确认、拒绝和手工版本

确认请求包含 `operation_id` 和 `expected_proposal_version`。事务：

1. 锁定本人提案、规划输入修订行和目标周 `Plan`。
2. 已应用提案直接返回同一应用结果；已拒绝提案拒绝应用。
3. 检查 7 天有效期、输入修订号和基础计划版本。
4. 使用当前数据再次运行全部硬约束校验。
5. 日提案把目标日块合并到当前周其他日期；周提案使用完整新周内容。
6. 写不可变 `PlanVersion`、计划块和未排项，切换 `Plan.current_version_id` 并递增版本。
7. 标记提案已应用，写操作去重和同步变更。

修订号或基础版本变化返回 `409 proposal_conflicted`，详情只列变化类别和当前版本，不回显不属于当前用户的对象。超期返回 `409 proposal_expired`。两类错误都保留提案供查看，并提供重新生成入口。

拒绝只修改提案状态，不写计划。重复拒绝返回同一结果；已应用提案不能拒绝。

手工保存接受完整周计划草稿、`expected_plan_version` 和 `operation_id`。服务端锁定输入修订行，复用同一硬约束校验，创建 `source=manual` 的新版本。拖拽只是客户端输入方式；时间字段、上移/下移和步骤选择是等价替代路径。

## 8. API

首版接口组：

| 方法与路由 | 作用 |
| --- | --- |
| `GET /api/v1/planning/context` | 读取日期范围、任务候选、固定占用、当前周计划和修订信息 |
| `POST /api/v1/planning/generations` | 独立规划页发起 AI 规划作业 |
| `POST /api/v1/ai/conversations/{id}/messages` | `response_mode=planning` 时从对话发起同一规划作业 |
| `GET /api/v1/proposals` | 分页读取本人提案 |
| `GET /api/v1/proposals/{id}` | 读取提案、变化、关联作业和有效状态 |
| `POST /api/v1/proposals/{id}/apply` | 幂等确认并创建周计划版本 |
| `POST /api/v1/proposals/{id}/reject` | 幂等拒绝 |
| `GET /api/v1/plans` | 按自然周范围读取当前计划摘要 |
| `GET /api/v1/plans/{id}` | 读取当前或指定历史版本 |
| `POST /api/v1/plans/{id}/versions` | 手工纠错并创建新版本 |
| `GET /api/v1/planning/blocks` | 给统一日历读取已确认计划块投影 |

所有接口只从认证上下文确定 `owner_id`。生成、确认、拒绝和手工保存均要求 CSRF 与操作 ID；查询不返回其他用户对象是否存在。

## 9. Web 交互

新增 `/plans`，产品导航顺序为 AI、任务、规划、日历、设置。

桌面：

- 左侧复用产品导航。
- 中间为范围、日期、密度、缓冲、可规划时段和任务选择。
- 主区域按日显示计划时间轴、固定占用、任务块、自由时间和未排项。
- 右侧或同一主区域顶部显示生成、提案、应用和保存状态。

平板将条件区折叠到顶部；840px 以下按日期分组为议程，不压缩七列时间轴；520px 以下使用单列和固定底部确认栏。所有图标按钮带名称，触控命中区至少 44px。

状态分层：

- 作业：排队、生成、校验、失败、超时、取消。
- 提案：可预览、应用中、已应用、已拒绝、已过期、输入冲突。
- 编辑器：未修改、已修改、保存中、已保存、保存状态未知。

提案卡明确显示“尚未写入计划”。确认后显示版本号并提供“在规划页查看”。AI 对话消息只渲染纯文本，提案卡从服务端 `proposal_id` 读取；不解析正文。

统一日历增加 `plan` 投影类型，只读取当前已确认版本。提案、生成中结果和历史版本不进入日历。计划块详情显示关联任务、步骤、来源版本和前往规划页入口，不提供误导性的任务完成操作。

## 10. 并发、容量和恢复

- 同一会话最多一个排队/执行作业；账号用户额度作业合计最多 3 个。
- 同一周确认和手工保存通过 `Plan` 行锁串行；首次创建依赖唯一约束并把冲突转换为版本错误。
- 规划快照最多 100 个候选、2000 个固定 occurrence 输入上限、100 个输出块；超限要求缩小范围。
- 数据库事务不跨供应商网络请求。worker 延续租约心跳、总截止、有界重试和单一终态。
- 页面离开不取消作业。独立规划页轮询作业快照；对话内继续使用持久化 SSE。完成后重新读取提案，不从事件拼装结构化 JSON。
- 服务端已提交但客户端超时时，原操作 ID 重试返回同一结果。
- 输入变化不自动重排已确认计划。ICS 订阅成功更新未来固定安排时，服务端持久化当前计划版本的
  来源复核记录；规划页显示前后时段并允许保留、手工修正或按最新来源重新生成，统一日历只标记
  实际重叠块。新整周计划版本解决旧提示，未确认提案不清除提示。

## 11. 测试与验收

模型与数据库：

- 迁移升降级、所有权复合外键、不可变计划版本、提案单次应用和触发器修订。
- 快照锁与并发任务/日历修改，结果只能串行为完整旧状态或完整新状态。
- 日/周、无截止、重复 occurrence、步骤进度、无课表、空任务和输入上限。
- 相邻端点、缓冲、跨午夜固定安排、DST 缺失/重复、日期型/定时截止、不可拆和过载。
