# iTime M8 性能与容量基线设计

版本：0.1；更新：2026-10-05。

## 1. 状态、目的与范围

本文定义 M8-A 的工程性能与容量基线，用于回答以下发布问题：

1. 在固定资源和固定进程拓扑下，初期约 100—1000 注册用户、日活不超过 100 的 Web
   服务能否稳定承载预期交互负载。
2. 普通 API、同步、AI 持久作业及其他后台队列是否相互隔离，负载增加时是否以有界错误失败。
3. 长历史、峰值、积压和耐久场景下，数据库连接、锁、CPU、内存和队列是否有明确上限。
4. 性能结果能否由同一提交、数据种子和资源配置重复执行，并形成可审计报告。

用户已确认同步约 5 秒目标、AI 约 3 分钟可配置总等待基线、初期规模和运营预算。本文中的
`2 vCPU / 4 GiB`、并发档位和接口分位数是 M8-A 采用的工程验收基线，不冒充公网 SLO、正式
供应商承诺或新的产品决定。生产候选资源与本基线不一致时必须使用独立环境标识重新执行，不能
直接沿用本地结果。

M8-A 包含隔离负载基础设施、确定性数据集、普通与异步场景、资源采样、报告门禁、负载下真实
浏览器验证，以及为达到门禁所必需的局部优化。以下内容不在本设计范围：

- 正式第三方模型质量和公网供应商延迟；
- M8-B 的备份恢复、RPO/RTO 和删除台账重放；
- M8-C 的公网域名、TLS、真实邮件、生产发布与回滚；
- 面向用户或管理员的新性能看板；
- 以缓存、降级或删减既有业务语义换取更好数字。

## 2. 当前基础与缺口

当前服务为 FastAPI 模块化单体、PostgreSQL 权威存储和数据库租约队列。API 已有结构化
`route/status/duration_ms/request_id` 日志；数据库连接池、连接/语句/锁/空闲事务超时集中
配置；AI、订阅、公开链接、导出、邮件和清理任务均在独立进程执行。

现有动态测试已经覆盖真实 HTTP/PostgreSQL、双连接并发、队列租约、重试、同步 5 秒上界及
完整 Web 流程，但不能证明：

- 固定资源下的 P50/P95/P99、吞吐和饱和点；
- 100 个账号和重历史账号的数据规模；
- 多进程连接池总预算与 PostgreSQL 锁等待；
- AI 或其他队列积压时普通 API 的隔离；
- 60 分钟运行中的内存、连接和队列趋势；
- 背景负载下的真实浏览器操作。

仓库当前没有专用负载工具、可重复大规模数据生成器或统一性能报告器。

## 3. 工具方案与取舍

采用 **Locust + Python 编排器 + PostgreSQL/容器采样器 + Playwright**。

选择原因：

- Python 场景可以直接表达现有 Cookie、CSRF、操作号、分页、SSE 和异步作业合同；
- Locust 提供稳定的并发调度、思考时间、分位数、吞吐、错误分类和无界面执行；
- 数据准备、资源采样和报告仍可使用仓库现有 Python 工具链；
- Playwright 只负责负载下真实用户体验，不代替服务容量数据。

未选择的方案：

| 方案 | 不采用为主方案的原因 |
| --- | --- |
| k6 + Python 数据准备 | 负载引擎成熟，但新增 JavaScript 场景和独立二进制，认证及业务合同需重复维护 |
| 自研 asyncio/httpx 压测器 | 依赖少，但分位数、调度精度、分布式扩展和报告可信度均需自行维护 |

Locust 只作为开发依赖，不进入服务运行依赖。负载发生器运行在固定资源边界外，并监测自身 CPU
与连接错误；发生器饱和时本次结果无效。

## 4. 固定参考环境

### 4.1 资源边界

被测系统运行在独立的 `itime-perf` Compose 项目中，总资源上限为：

| 资源 | 基线 |
| --- | --- |
| CPU | 2 vCPU |
| 内存 | 4 GiB，包含 PostgreSQL、API 和常驻业务 worker |
| PostgreSQL | 18.x 固定镜像摘要；`max_connections=50`；性能环境启用 `pg_stat_statements` |
| API | 2 个 Uvicorn worker |
| AI worker | 2 个进程 |
| 其他 worker | 邮件、订阅、公开链接、导出各 1 个进程 |
| 周期清理 | 在专用维护场景中运行，不与普通稳态场景无条件叠加 |
| 外部协议桩 | 运行在资源边界外，提供可配置延迟、流式输出、限流、断流和失败 |
| 负载与浏览器 | 运行在资源边界外，不占用被测系统 CPU/内存预算 |

前端使用当前提交的生产构建。静态文件服务和负载发生器不计入本次 API/数据库容量；M8-C
需要在最终反向代理和网络拓扑上重新执行上线前短基线。

### 4.2 数据库连接预算

不同进程通过环境配置使用不同连接池：

| 角色 | 进程数 | 单进程池 | 理论上限 |
| --- | ---: | ---: | ---: |
| API | 2 | `pool_size=4`、`max_overflow=1` | 10 |
| AI worker | 2 | `pool_size=1`、`max_overflow=0` | 2 |
| 邮件/订阅/链接/导出 | 4 | `pool_size=1`、`max_overflow=0` | 4 |
| 迁移、采样和受控维护 | 按阶段 | 最多 1 条活动连接/进程 | 4 |
| 合计预算 |  |  | 20 |

所有池均为惰性建立；理论预算仍必须低于 PostgreSQL 上限。连接采样同时记录活动、空闲、空闲
事务、等待和按 application name 分组的数据，不以“当前只开了少量连接”替代理论预算检查。

## 5. 安全与隔离

性能入口必须同时满足：

1. 目标 HTTP origin 是回环地址或当前随机 Compose 网络内地址；
2. 数据库名称以 `itime_perf_` 加随机标识开头；
3. `ITIME_ENVIRONMENT=test`，且数据库包含本次运行写入的随机安全标记；
4. Compose 项目名、卷和网络均以本次运行标识命名；
5. 未设置任何正式 SMTP、AI 或第三方订阅凭据；
6. 并发执行锁不存在，避免两个运行争用同一端口或资源档位。

任一条件不满足即在创建数据前退出。清理只允许操作本次清单记录的数据库、容器、卷、网络、
端口和进程，不使用宽泛名称匹配。不得连接生产、发送外部邮件、访问真实订阅源或调用付费模型。

每次运行生成临时 Fernet 密钥、账号密码和协议桩凭据；它们只存在于权限受限的临时目录，不写
报告、日志或仓库。

## 6. 确定性数据集

数据生成器接受固定随机种子和基准时间，结果按账号、对象类型和生命周期状态可计数。大量历史
数据通过受控服务/数据库播种器建立，随后执行数据库约束、所有权、版本、索引可用性和业务读取
校验；被测工作负载始终通过真实 HTTP API。

### 6.1 标准数据集

创建 100 个账号，其中 20—50 个按场景成为活动虚拟用户。每个活动账号包含：

- 24 个项目、40 个标签和约 300 个活动/已归档/回收站任务；
- 单次及重复任务、步骤、完成/跳过事实和公开链接安全快照；
- 约半年课程、固定安排、日历例外、订阅投影和当前计划；
- 约 180 条专注事实、90 条困难、90 个复盘活动日和适量长期记忆；
- 20 个普通会话，每个会话约 40 条消息；
- 至少 3000 条无正文同步变更事件；
- 用户额度、成本、审计和生命周期状态的代表记录。

非活动账号仍保留轻量数据，用于验证总账号规模和索引选择，不在稳态中同时发请求。

### 6.2 重历史数据集

另建 5 个重历史账号，各自接近已有服务边界：

- 1000 个任务/任务日程；
- 1000 个候选日历系列及最多 5000 个订阅来源事件；
- 5000 条普通对话消息；
- 跨一年计划、执行、困难、复盘、记忆和统计事实；
- 10000 条同步事件及跨多个分页游标的历史。

重历史场景用于发现查询计划、N+1、投影展开和序列化问题，不把超出产品硬上限的数据强行写入
数据库。

## 7. 负载模型

虚拟用户使用 1—3 秒确定性分布的思考时间。普通混合流量按实际页面请求组合而非只调用健康
检查：

| 流量类别 | 权重 | 代表操作 |
| --- | ---: | --- |
| 任务与搜索 | 25% | 列表、筛选、详情、步骤状态和小批量写 |
| 日历与计划 | 20% | 7/31/93 天 occurrence、计划块、规划上下文 |
| 同步 | 20% | 状态、增量分页、写后跨端可见 |
| 执行、复盘、统计 | 20% | 当前专注、困难分页、复盘详情、日周月统计 |
| 账号与额度 | 10% | 本人信息、设备、额度摘要和账本 |
| 受控写入 | 5% | 创建任务、困难和专注状态变更，全部使用唯一操作号 |

场景矩阵：

| 场景 | 负载 | 目的 |
| --- | --- | --- |
| 预热 | 5 用户，3 分钟 | 建立连接、缓存和 Python 热路径；结果不计入门禁 |
| 稳态 | 20 用户，15 分钟 | 初期日活下的主要发布门禁 |
| 峰值 | 50 用户，5 分钟 | 晚间集中使用和短时突发 |
| 重历史 | 10 个重历史用户，10 分钟 | 分页、搜索、日历展开、统计和同步长历史 |
| 饱和 | 10 起每 3 分钟增加 10，最多 100 | 找到连续三个窗口违反门禁前的最大稳定档位 |
| AI 隔离 | 20 普通用户 + 20 个 AI 作业，2 个 AI worker | 队列、慢流、额度和普通 API 隔离 |
| 其他队列 | 订阅、公开链接、导出分别制造积压 | 单 worker 吞吐、租约、连接占用和积压恢复 |
| 维护 | 到期清理和同步事件清理批次 | 清理吞吐、锁影响及 API 隔离 |
| 耐久 | 20 用户，60 分钟 | 内存、连接、锁、文件和队列趋势 |

AI 隔离场景的协议桩默认在 10 秒内持续返回流式结果，并可切换为 429、503、断流和超时。故障
场景用于验证有界切换与释放，不将预期重试时间混入正常成功分位数。

## 8. 性能门禁

### 8.1 请求与同步

| 指标 | 门禁 |
| --- | --- |
| 稳态普通读取 | P95 ≤ 500 ms；P99 ≤ 1 s |
| 稳态普通写入 | P95 ≤ 800 ms；P99 ≤ 1.5 s |
| 50 用户峰值普通请求 | P95 ≤ 1 s；P99 ≤ 2 s |
| 重历史查询 | P95 ≤ 1.5 s；P99 ≤ 3 s |
| 同步写入到另一端可见 | P95 ≤ 3 s；P99 ≤ 5 s |
| 非预期请求失败率 | ≤ 0.1% |
| 服务端 5xx | 0 |

登录密码计算、文件上传、下载和 SSE 长连接分别统计，不混入普通请求分位数。同步端到端时延从
成功业务写开始，到另一虚拟设备从增量同步读取到对应事件并完成必要重读为止。

### 8.2 AI 与隔离

在 10 秒受控上游、20 个同时提交作业和 2 个 AI worker 的场景中：

| 指标 | 门禁 |
| --- | --- |
| HTTP 接单 | P95 ≤ 1 s |
| 接单到首次领取 | P95 ≤ 30 s |
| 上游首段到用户 SSE 可见 | P95 ≤ 2 s |
| 作业端到端完成 | P99 ≤ 60 s |
| 普通 API 退化 | P95 不超过无 AI 积压稳态的 2 倍，且绝对值 ≤ 1 s |
| 终态与金额 | 无丢失、重复应用、重复结算、活动预留残留 |

429、503、断流和超时场景按既有错误合同验证重试、备用切换和 180 秒总截止，不要求故障作业
达到正常成功分位数，但普通 API 隔离、终态唯一和预留释放仍是硬门禁。

### 8.3 资源与容量

| 指标 | 门禁 |
| --- | --- |
| 稳态 CPU | 1 分钟均值 ≤ 70% 总配额 |
| 峰值 CPU | 不连续 60 秒超过 90% |
| 内存 | 峰值 ≤ 85% 配额；耐久后 30 分钟无持续上升趋势 |
| 数据库连接 | 峰值 ≤ 连接预算的 80%；无连接池超时 |
| 锁 | 无超过 2 秒的阻塞锁；无死锁 |
| SQL | 无语句超时；慢查询必须进入报告并有查询计划 |
| 文件/进程 | 无持续增长的临时文件、子进程或文件描述符 |
| 最低容量 | 50 个带思考时间的并发用户通过峰值门禁 |

饱和测试达到门禁外档位属于容量发现，不自动导致整次失败；若 50 用户档位未通过则 M8-A
失败，必须优化或明确提高参考资源后重新执行。

### 8.4 浏览器门禁

稳态背景负载期间执行 Chromium desktop/mobile/tablet 和真实 Edge desktop：

- 登录、任务列表/详情、日历、计划、专注、复盘、统计和同步状态可达；
- 关键页面操作在 5 秒内完成或显示符合业务合同的异步状态；
- 无未预期控制台 error、API 5xx、Vite/框架错误覆盖层、空白页面或根级横向溢出；
- 跨端写入仍在 5 秒内可见；
- 页面失败时仍显示是否保存、恢复操作和请求编号。

本场景验证负载下可用性，不用浏览器计时代替 Locust 的服务分位数。

## 9. 组件与数据流

### 9.1 组件

| 组件 | 职责 |
| --- | --- |
| `compose.performance.yaml` | 建立固定资源、固定版本、独立网络和临时卷的被测系统 |
| `performance/run.py` | 安全校验、生命周期编排、场景调度、信号处理和退出码 |
| `performance/seed.py` | 按种子创建标准/重历史数据并输出数据清单 |
| `performance/locustfile.py` | 真实认证、CSRF、分页、同步、SSE、写入和队列用户行为 |
| `performance/upstream.py` | 可控 AI/SMTP/ICS/公开网页协议桩 |
| `performance/sampler.py` | 容器、进程、PostgreSQL、连接、锁、SQL 和队列采样 |
| `performance/report.py` | 合并原始数据、执行门禁并生成 JSON/CSV/Markdown |
| `web/e2e/performance-under-load.spec.ts` | 背景负载下真实浏览器流程 |

负载工具不通过测试专用生产路由修改业务数据。仅数据准备器可直接访问隔离数据库；实际工作流
全部调用真实 API 和真实 worker。

### 9.2 执行流

1. 编排器校验环境和互斥锁，创建随机运行 ID、端口、临时目录和 Compose 项目。
2. 启动 PostgreSQL，创建 `itime_perf_<run_id>`，运行当前 Alembic head。
3. 数据生成器播种并核对清单；启动 API、worker 和受控协议桩。
4. 预热完成后重置 Locust、`pg_stat_statements` 和资源采样窗口。
5. 每个场景独立运行；采样器每秒记录资源和队列，Locust 记录请求和自定义端到端事件。
6. 场景结束后等待受控队列排空，核对数据库不变量并生成单场景结论。
7. 汇总器生成总报告；无论成功、失败、SIGINT 或子进程退出，均进入精确清理。
8. 清理后再次查询容器、卷、网络、进程和 `itime_perf_*` 数据库，残留非零使运行失败。

## 10. 观测与报告

### 10.1 请求指标

- 方法、路由模板、状态、请求数、吞吐、P50/P95/P99、最大值和失败码；
- 登录、上传、下载、SSE、普通读和普通写分别分组；
- 同步写入到另一端可见、AI 接单/排队/首段/完成使用 Locust 自定义事件；
- 服务端结构化日志按请求编号与客户端失败样本关联。

### 10.2 资源与数据库指标

- 每容器 CPU、RSS/工作集、内存限制、网络和块 I/O；
- API/worker 进程数、RSS、CPU 和文件描述符；
- PostgreSQL 活动/空闲/空闲事务连接、等待事件、锁等待、事务提交/回滚和临时文件；
- `pg_stat_statements` 的调用次数、总时间、平均时间、返回行、共享块和临时块；
- SQLAlchemy 连接池超时通过错误日志和请求错误码核对；
- AI、订阅、公开链接、导出、邮件和清理队列的 queued/running 数、最旧可领取时间和终态速率。

### 10.3 产物

运行目录默认位于 `/tmp/itime-performance/<run_id>/`：

- `manifest.json`：提交 SHA、时间、资源、镜像摘要、进程、种子和场景参数；
- `requests.csv/json`：Locust 原始统计；
- `resources.csv`、`postgres.csv`、`queues.csv`：时序采样；
- `failures.json`：类型化失败和请求编号，不含正文或凭据；
- `summary.json`：机器可读门禁结论；
- `report.md`：人工可读摘要、瓶颈、饱和点和限制；
- `logs/`：受限结构化日志。

仓库只提交可复核的基线摘要和必要的小型 JSON，不提交 Cookie、CSRF、密码、密钥、完整 URL、
用户正文或大体积原始日志。

## 11. 错误处理与恢复

- 普通请求不自动重试，以免隐藏真实失败或重复写；幂等恢复场景显式复用原 operation ID。
- 只有场景声明的 409、429 或 503 且错误码完全匹配时才记为预期结果；其他响应均计失败。
- 负载发生器自身 CPU 持续超过 80%、时钟跳变、连接耗尽或采样缺口超过 5 秒时，结果标记
  `invalid`，不得写成通过或失败容量结论。
- 任一服务提前退出时停止新增负载，等待在途样本有界结束，写入部分报告并执行清理。
- 数据库不变量、金额、作业终态或清理残留失败时，即使延迟达标也判为失败。
- 阶梯饱和超过门禁后停止继续加压，等待队列排空和资源回落，避免无价值的资源耗尽。
- 性能优化不得放宽所有权、事务、版本、超时、额度、生命周期或 AI 确认合同。

## 12. 测试与验收

### 12.1 工具自身测试

- 数据种子相同则对象计数、时间和关系稳定，不同运行 ID 不冲突；
- 分位数、窗口均值、趋势、阈值边界和预期错误分类有单元测试；
- 非回环 origin、非 `itime_perf_*` 数据库、生产环境和错误安全标记均被拒绝；
- SIGINT、容器失败、Locust 失败、采样失败和报告失败仍执行精确清理；
- 报告递归扫描敏感键和测试秘密，发现后拒绝产出。

### 12.2 动态验证

1. 2 用户、30 秒的完整编排烟测，包含迁移、播种、HTTP、worker、采样、报告和零残留。
2. 标准数据集下执行稳态、峰值和饱和场景。
3. 重历史数据集下执行分页、搜索、日历、统计、同步和导出场景。
4. 可控上游下执行 AI 正常、429/503、断流、超时及普通 API 隔离。
5. 分别制造订阅、公开链接、导出和维护积压，验证租约、吞吐和排空。
6. 执行 60 分钟耐久测试并检查资源趋势。
7. 稳态背景负载期间执行 Chromium 三视口及真实 Edge desktop。
8. 所有必要优化完成后执行 Ruff、服务端全量 pytest、构建、前端构建及受影响 Web 回归。

### 12.3 完成条件

M8-A 只有同时满足以下条件才可标记完成：

- 固定参考环境、镜像、进程、连接预算和数据清单可重建；
- 50 用户峰值及全部硬门禁通过；
- 饱和点、主要瓶颈和扩容触发条件有实测数字；
- AI/队列积压不破坏普通 API、金额和终态一致性；
- 60 分钟耐久测试无持续资源增长；
- 负载下 Chromium 三视口与真实 Edge desktop 通过；
- 全量或明确受影响回归通过；
- 测试数据库、容器、卷、网络和临时进程零残留；
- 实施记录只陈述真实执行结果，并保留公网、正式模型、备份和发布的未完成边界。
