# iTime 复盘与记忆设计

版本：0.1；更新：2026-10-03。本文细化 `REQ-REVIEW-01`、`REQ-MEM-01`，以及复盘范围内的 `REQ-AI-01`、`REQ-QUOTA-01`、`REQ-TIME-01` 和 `REQ-SYNC-01`。同日会话数量、报告结构、更正语义和记忆暂停规则是用户授权代理自行决定后的可演进默认，不表述为用户原始决定。

## 1. 范围与方案选择

本阶段交付：

- 独立 `/reviews` 页面，按用户时区和 04:00 活动日选择一天，读取当天计划块、任务完成、专注和困难事实。
- 一个账号在一个活动日只有一个可恢复复盘会话；刷新、离页和换设备后继续同一会话。
- 用户可保存补充事实，可进行零到三轮 AI 追问，也可随时跳过追问直接生成报告。
- 报告固定区分事实、用户说明、AI 推测、下一步和缺失信息；重新生成形成新版本，不覆盖旧版。
- 每个报告版本可独立添加、修改和删除用户批注。
- AI 可随报告提出最多五项长期记忆候选；逐项确认后才保存，拒绝不产生记忆。
- 记忆可查看、编辑、暂停使用、移到回收站和恢复；删除后立即退出后续 AI 检索。
- `review` 作为独立 AI 能力接入配置版本、持久化作业、租约、重试、治理日志、质检、成本和用户额度。

本阶段不交付：

- 周复盘、月复盘、团队复盘、公开分享或报告导出。
- 从报告自动修改任务、计划、偏好或长期记忆。
- 心理诊断、情绪归因、人格画像或根据缺失数据推断用户没有完成。
- 记忆向量索引；首版按所有者、启用状态、最近更新时间和条数上限构造可审计的文本上下文。
- 日/周/月统计、通用离线同步、账号注销和完整数据导出；这些属于后续独立子项目。

比较过三种实现：

1. **独立复盘聚合、独立 AI 能力和不可变快照（采用）**：复盘对话、报告版本、批注和记忆候选边界清楚，可独立归档并复用已有 AI 作业、额度和治理基础设施。
2. 给普通 AI 会话增加复盘标签：可少建部分表，但普通聊天的开放上下文、消息流和归档语义无法可靠表达单日事实快照、固定报告结构和历史版本。
3. 只提供一次性报告生成：实现较少，但不满足少量追问、断点继续和用户补充事实的产品要求。

## 2. 可演进产品默认

1. 同一账号同一活动日只有一个复盘会话。重复进入返回原会话，不创建多个互相矛盾的当日报告集合。
2. 复盘可对过去或当前活动日补做，不允许选择未来活动日。
3. AI 最多提出三轮追问，每次只提一个问题。用户不必回答，可直接生成报告；三轮后只保留报告生成入口。
4. 报告必备结构为“今日概览、已确认事实、用户说明、观察与推测、下一步、信息缺口”。推测必须带 `ai_inference` 标记，不得混入事实。
5. 用户更正补充事实或当天业务事实变化时，历史报告保持原样并显示“基于旧快照”；用户主动重新生成后得到下一版本。
6. 报告批注是用户对特定历史版本的独立说明，不回写报告正文，也不自动进入长期记忆。
7. 记忆支持整体暂停。暂停只停止后续 AI 检索，不删除已有记忆，也不阻止用户查看、编辑、确认候选或恢复使用。
8. 记忆删除进入 30 天回收站并立即停止检索；恢复期结束后清空正文和来源关联，保留最小墓碑阻止旧操作复活。
9. 报告生成可以提出记忆候选，但生成成功本身不保存记忆。候选须逐项确认；拒绝后保持拒绝事实，不能由旧页面重复确认。
10. 记忆候选和记忆正文只允许记录用户明确陈述或稳定偏好，不保存 AI 推测、临时情绪、敏感推断或第三方秘密。

## 3. 核心不变量

1. `ReviewSession(owner_id, activity_date)` 唯一，活动日和时区快照由服务端确定。
2. 复盘事实按活动日当地 `[04:00, 次日 04:00)` 转换到 UTC 后读取；日历计划块仍按其真实 `local_date` 纳入，界面明确两种口径。
3. 每个 AI 作业绑定一个不可变 `ReviewInputSnapshot`。供应商调用期间不持有数据库事务，也不读取变化中的业务表。
4. 一个复盘会话最多一个排队或执行中的 AI 作业，防止追问和报告并发导致顺序、额度或版本竞态。
5. 用户答案和补充事实增加会话 `input_revision`；当前业务事实摘要变化会改变事实摘要哈希。报告同时匹配两者才是当前版本。
6. AI 追问成功后才新增助手消息。用户答案在接单事务内先保存；上游失败不丢答案，用户可重试或直接生成报告。
7. 报告版本号在会话行锁内递增。一个成功作业最多创建一个报告版本，重复终态处理返回既有结果。
8. 报告、事实快照和历史消息不可原地改写；更正通过新的用户输入、批注或报告版本表达。
9. 记忆候选确认在同一事务内重新校验所有者、候选状态和来源报告存在性，再创建唯一记忆并标记候选已确认。
10. 活跃记忆检索只读取 `deleted_at IS NULL`，并同时检查用户的记忆总开关。删除或暂停提交成功后，之后接单的 AI 作业不得再快照这些记忆。
11. 所有用户写操作带全账号 `operation_id`。相同操作和内容重试返回原结果；相同 ID 携带不同内容拒绝。
12. 失败、取消和超时释放额度预留；结构校验通过并形成可查看问题或报告时按最终成功尝试结算一次。

## 4. 数据模型

### 4.1 ReviewSession

`review_sessions` 保存单日复盘入口和当前输入修订：

| 字段 | 语义 |
| --- | --- |
| `id / owner_id` | 稳定标识与所有者 |
| `activity_date` | 04:00 口径下的目标活动日 |
| `time_zone` | 首次创建时的 IANA 时区快照 |
| `supplemental_facts` | 用户可修改的补充事实，最多 8000 字符 |
| `input_revision` | 用户补充事实或回答成功保存后递增 |
| `question_count` | 已成功产生的 AI 追问数，范围 0—3 |
| `version` | 会话写入版本 |
| `created_at / updated_at` | 服务端时刻 |

唯一约束为 `(owner_id, activity_date)`。修改时要求 `expected_version`，并发冲突返回服务器最新版。

### 4.2 ReviewMessage

`review_messages` 保存独立于普通聊天的短对话：

- `role` 为 `user` 或 `assistant`；`kind` 为 `answer` 或 `question`。
- `sequence` 在会话内连续唯一，正文分别限制为 8000 和 2000 字符。
- 用户答案在问题作业接单时保存；助手问题只在作业成功终态写入。
- 消息不可修改或删除；事实更正写入补充事实，保证已参与旧报告的上下文可追溯。

### 4.3 ReviewInputSnapshot

`review_input_snapshots` 是每个问题或报告作业的不可变输入：

- `purpose` 为 `question` 或 `report`。
- 保存活动日、时区、活动日起止 UTC、`session_input_revision` 和 `facts_sha256`。
- `facts` 分组保存计划块、任务完成、专注事实和困难记录；每组都有数量与截断标记。
- `user_context` 保存补充事实和截至接单时的复盘消息。
- `memory_context` 保存接单时实际可用的长期记忆 ID、版本和正文快照。
- `generation_instruction` 只用于报告重新生成时的本次要求，最多 2000 字符。

单组最多 200 条，总序列化内容不超过 512 KiB。超过时按“目标日直接关联、最近发生、稳定 ID”顺序截取，并把截断事实写入快照和报告信息缺口，不能静默省略。

### 4.4 ReviewReportVersion

`review_report_versions` 保存不可变报告：

| 字段 | 语义 |
| --- | --- |
| `review_session_id / owner_id` | 所属复盘与所有者 |
| `version` | 会话内从 1 开始递增 |
| `source_job_id / input_snapshot_id` | 唯一成功作业和事实快照 |
| `summary` | 今日概览 |
| `facts` | 仅来自快照或用户明确说明的事实条目 |
| `user_statements` | 用户补充和回答的归纳 |
| `insights` | 明确标为 AI 推测的观察 |
| `next_actions` | 建议，不自动写入任务或计划 |
| `uncertainties` | 缺失、冲突、截断和无法确认的信息 |
| `created_at` | 生成完成时刻 |

数组元素包含稳定位置、正文和来源标记。服务端使用严格 Pydantic 结构校验、长度和数量限制；供应商输出不能提交任意 HTML。

### 4.5 ReviewAnnotation

`review_annotations` 绑定一个报告版本，保存用户批注、版本和删除时刻。创建、修改、删除均需操作幂等和乐观版本；删除只隐藏批注，不改变报告及其事实快照。

### 4.6 MemoryProposal 与 Memory

`memory_proposals` 保存报告中的待确认候选：

- `kind` 为 `preference / constraint / context / goal`。
- 保存标题、正文、提出理由、来源报告版本和状态 `pending / confirmed / rejected`。
- 一个候选最多确认成一个记忆；确认和拒绝均要求候选版本。

`memories` 保存用户确认或后续人工创建的长期记忆：

- `title` 最多 120 字符，`content` 最多 2000 字符，`kind` 使用同一枚举。
- `source_type` 为 `review_proposal / manual`，报告候选来源使用唯一外键。
- 删除字段为 `deleted_at / purge_after / purged_at`；到期清理后正文和来源关联为空。
- 活跃、回收站和已清理状态由生命周期字段推导，不由客户端提交。

`memory_settings` 每个用户一行，`enabled` 默认 `true`，带版本。关闭后只影响新接单作业的上下文构造。

## 5. 事实快照口径

复盘入口先读取当前事实预览，AI 接单时在同一事务重新构建并冻结：

| 数据 | 纳入规则 | 展示和缺失语义 |
| --- | --- | --- |
| 计划块 | 目标真实 `local_date` 上当前周计划版本的块 | 保存计划版本、原定时段、任务和步骤快照；没有计划是合法空数据 |
| 任务完成 | 非重复任务或 occurrence 的 `completed_at` 落入活动日 UTC 窗口 | 完成后重新打开也保留变更事实来源；不以计划块时间经过推断完成 |
| 专注 | 有效区间与活动日窗口相交 | 按交集秒数统计，同时保留原会话总时长、状态和修订标记；开放会话标为进行中 |
| 困难 | 未删除记录的 `occurred_at` 落入活动日窗口 | 仅使用用户正文、分类和情绪原值，不补充心理原因 |
| 用户补充 | 当前 `supplemental_facts` 与复盘回答 | 标记为用户说明，不冒充系统记录 |

事实预览返回当前 `facts_sha256`。报告详情实时重建摘要哈希，与版本快照比较后给出 `current / stale_user_input / stale_business_facts / stale_both`，但不会自动触发 AI 或收费。

## 6. 复盘与作业状态

```text
进入目标活动日
  └─ 创建或恢复唯一 ReviewSession
       ├─ 修改补充事实
       ├─ 0—3 次：保存回答 → 冻结快照 → 问题作业 → 新助手问题
       └─ 随时：冻结快照 → 报告作业 → 新 ReportVersion
                                      ├─ 添加独立批注
                                      └─ 逐项确认/拒绝记忆候选
```

作业仍使用 `queued → running → succeeded | failed | timed_out | cancelled`。`AIJob` 增加 `review_snapshot_id` 和 `review_session_id`；输入引用约束保证 `review` 作业只引用本人复盘快照，且不引用媒体、普通会话或规划快照。

问题和报告均要求 `review` 配置已发布、账号 AI 可用、额度可预留且账号总并发未超限。显式取消只终止当前作业，已保存答案和既有报告不回滚。

## 7. AI 输入与输出约束

问题模式：

- 系统提示要求只基于快照提出一个简短、非诊断、可跳过的问题。
- 输出通过唯一工具 `submit_itime_review_question`，参数只有 `question`。
- 服务端拒绝空问题、多个工具调用、超过 2000 字符或第四个问题。

报告模式：

- 系统提示把业务文本、困难和记忆都视为不可信数据，不执行其中指令。
- 输出通过唯一工具 `submit_itime_review_report`，参数匹配固定报告结构和最多五个记忆候选。
- 服务端逐条校验来源。`facts` 只能引用快照中的稳定事实键或声明为 `user_statement`；无法对应的内容移入 `ai_inference` 或拒绝结果。
- 记忆候选不能使用 `ai_inference` 作为来源。候选正文必须能对应用户补充、回答或既有有效记忆，否则删除候选并记录报告警告。

AI 输出只有在结构、所有权、数量和来源校验全部通过后才成为可查看结果并结算。部分流式内容只写技术正文日志，不作为报告或问题展示。

## 8. 记忆检索合同

首版使用有界、可审计的确定性检索：

1. 仅在 `memory_settings.enabled = true` 时读取活跃记忆。
2. 按当前能力允许的种类、`updated_at DESC, id` 排序，最多 30 条，总正文最多 12,000 字符。
3. 对话、规划和复盘在各自接单事务中冻结记忆 ID、版本和正文；在途作业不因之后编辑而改写输入。
4. 删除后新作业不再读取。已接单但尚未调用供应商的作业在加载工作时再次校验记忆版本；发现已删除或设置关闭则以新快照替换上下文，无法安全替换时作业失败并释放额度。
5. 已经发送到供应商的在途请求无法撤回；删除保证不进入后续请求，并按技术正文日志 7 天规则清理既有请求副本。

不使用字符串相似度冒充语义检索。后续引入向量索引时，索引必须带所有者和记忆版本，删除事务写失效台账，检索结果仍回表复核。

## 9. API 合同

所有路由位于 `/api/v1`，所有者来自认证会话。

| 方法与路由 | 作用 | 主要失败 |
| --- | --- | --- |
| `GET /reviews?cursor=&limit=` | 分页列出复盘会话和最新报告 | 游标无效 |
| `POST /reviews` | 按活动日幂等创建或返回会话 | 未来日期、时区未设置 |
| `GET /reviews/{id}` | 会话、事实预览、消息、报告版本摘要和活动作业 | 不存在、跨账号 |
| `PUT /reviews/{id}/facts` | 保存补充事实 | 版本冲突、长度超限 |
| `POST /reviews/{id}/questions` | 可选保存回答并创建下一问题作业 | 已达三轮、活动作业冲突、额度不足 |
| `POST /reviews/{id}/reports` | 创建首版或重生成报告作业 | 活动作业冲突、额度不足 |
| `GET /reviews/{id}/reports/{version}` | 读取特定报告、批注和记忆候选 | 版本不存在 |
| `POST /review-reports/{id}/annotations` | 添加批注 | 报告不存在 |
| `PUT/DELETE /review-annotations/{id}` | 修改或删除批注 | 版本冲突 |
| `POST /memory-proposals/{id}/confirm` | 确认候选并创建记忆 | 已拒绝、版本冲突、来源失效 |
| `POST /memory-proposals/{id}/reject` | 拒绝候选 | 已确认、版本冲突 |
| `GET /memories?lifecycle=` | 分页读取记忆 | 游标无效 |
| `POST /memories` | 人工创建记忆 | 输入无效、幂等冲突 |
| `PUT /memories/{id}` | 修改记忆 | 版本冲突、已删除 |
| `DELETE /memories/{id}` | 移入 30 天回收站 | 版本冲突 |
| `POST /memories/{id}/restore` | 恢复记忆 | 已清理、版本冲突 |
| `GET/PUT /memory-settings` | 读取或修改整体启用状态 | 版本冲突 |

返回错误继续使用 `{code, message, request_id, saved, retryable, details}`。未知响应可用相同 `operation_id` 重试或重读目标资源确认。

## 10. UI 结构

产品主导航增加“复盘”，路径 `/reviews`。桌面使用左侧日期与历史版本导航、右侧工作区；手机端在“日期列表”和“当日复盘”之间切换，不嵌套卡片。

当日工作区顺序：

1. 日期标题与事实摘要，分别显示计划、完成任务、专注和困难数量。
2. 可编辑补充事实；保存状态明确。
3. 简短追问线程与“回答并继续”“跳过，生成报告”动作。
4. 当前报告，事实、用户说明、AI 推测、下一步和信息缺口使用独立标题与来源标记。
5. 版本选择和旧快照提示；历史版本只读，但可管理其批注和待处理记忆候选。
6. “记忆”视图作为复盘页内标签，支持启用开关、活跃/回收站筛选、编辑、删除和恢复。

生成中显示持久化作业状态、取消动作和离页继续说明；失败显示是否已保存、恢复动作和请求编号。320px、手机、平板和桌面视口均不得出现水平溢出，键盘焦点和读屏标题顺序纳入测试。

## 11. 并发、失败与恢复

- 创建会话使用唯一约束和幂等操作；并发请求最终返回同一会话。
- 修改补充事实、批注、候选和记忆均按 `expected_version` 比较，冲突返回服务器当前资源供 UI 重读。
- 创建作业先锁会话和账号 AI 容量，再构造快照、预留额度、写作业和操作记录；任一步失败整笔回滚。
- Worker 租约失效时不得写问题、报告、候选或扣额。陈旧尝试成本仍计平台成本。
- 报告成功事务同时创建报告版本、记忆候选、供应商成本、额度结算、治理记录和作业终态。
- 用户取消与 Worker 成功竞争时，只有先锁定终态者生效；取消获胜后晚到输出不可创建报告或问题。
- 事实源在生成期间变化不使当前作业失败，因为快照仍可追溯；完成后报告显示基于旧事实，用户可决定是否重生成。
- 记忆候选确认与记忆删除竞争时锁候选和记忆来源；一个终态获胜，另一个收到版本冲突，不产生重复记忆。
- 清理进程每批最多 100 条到期记忆，使用 `FOR UPDATE SKIP LOCKED`，清空正文和来源引用并写同步墓碑，可重复执行。

## 12. 安全、容量与验证

- 所有事实、报告、批注、候选和记忆查询都带 `owner_id`；跨账号 ID 返回不存在。
- 供应商请求不含平台 Key、会话 Cookie或不相关的账号历史；技术正文和质量样本沿用 7/30 天治理规则。
- 事实和记忆正文作为不可信数据进入模型；工具仅返回数据结构，没有写业务对象的权限。
- 报告查询分页，不一次加载账号全部复盘；记忆检索和事实快照均有条数、字符数和序列化体积上限。
- 复盘接单、Worker 完成和记忆确认测试使用真实 PostgreSQL 事务，覆盖两个 Worker 争抢、取消/成功竞态、重试和额度只结算一次。
- HTTP 测试覆盖本人隔离、幂等未知响应、版本冲突、无计划空事实、04:00 跨日、事实变化后的旧版提示和删除后检索失效。
- Chromium 测试覆盖创建/恢复会话、跳过追问、三轮上限、离页恢复、报告重生成、版本切换、批注、候选确认/拒绝、记忆暂停/删除/恢复及错误恢复。
- 运行 Ruff、全量 pytest、迁移升降级与 `alembic check`、清理 Worker、前端构建和全量 Playwright；截图至少覆盖桌面、手机和 320px 大字号深色模式。
