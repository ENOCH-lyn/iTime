# iTime 订阅来源计划冲突设计

版本：0.1；更新：2026-10-04。本文冻结 `REQ-CAL-03` 中“ICS 订阅来源更新后，指出已确认
计划冲突且不静默重排”的服务端、同步和 Web 合同。它补充
[ICS 订阅设计](iTime-ICS订阅设计.md)与
[AI 提案与日周规划设计](iTime-AI提案与日周规划设计.md)，不改变订阅只读、计划版本不可变和
业务写操作须由用户确认的既有规则。

## 1. 目标与非目标

目标：

- 只有成功应用的订阅日程变化才影响计划；304、抓取失败、解析失败和仅技术状态变化不制造计划
  冲突。
- 已确认计划内容和版本保持不变。来源刷新不能移动、删除或新增计划块。
- 用户可看到哪个来源、哪次刷新、哪些未来时段变化，以及是否与具体计划块重叠。
- 用户可明确选择保留当前计划，或基于最新来源重新生成/手工保存新计划版本。
- 冲突创建、来源修订、规划输入 revision 和同步事件原子提交，跨标签及跨设备能读取同一状态。
- 来源再次变化、计划并发更新、重复请求和账号删除均有确定结果。

非目标：

- 不自动调用 AI，不在后台生成新提案，也不因来源变化扣额度。
- 不把普通课程、手工固定安排或任务变更都扩展为同一持久冲突模型；本批只补齐 ICS 订阅来源。
- 不实现订阅 occurrence 的用户单次例外；该缺口继续独立处理。
- 不把“来源取消后腾出时间”伪装成实际时间重叠。界面区分“计划需复核”和“与计划块重叠”。

## 2. 方案选择

评估三种方案：

1. **持久化来源冲突记录（采用）**：每个当前计划版本、订阅来源和成功来源代次最多一条记录，
   保存变更前后投影和重叠块。可审计、可同步、可精确确认处理，代价是新增表及生命周期。
2. 读取计划时动态重算：不新增表，但无法证明用户看到的是哪次刷新，也不能在来源再次变化后保留
   处理语义；跨设备只能轮询猜测，不采用。
3. 在 `Plan` 或 `ScheduledBlock` 上保存布尔标志：实现简单，但来源取消或释放空档未必对应某个
   计划块，单个标志也无法表达多个来源和用户处理结果，不采用。

采用来源级聚合而非每个 occurrence 一行。一个刷新代次在一个计划版本上只创建一条冲突记录，
`changes` 内保存该周受影响 occurrence；既限制列表噪音，也保留足够的恢复证据。

## 3. 冲突判定

### 3.1 比较范围

订阅 worker 成功取得完整快照后，在应用来源事件前后分别投影：

- 账号所有“当前版本仍生效”的本周或未来周计划；
- 每个计划自身的周一 `00:00` 到下一周周一 `00:00`，按计划保存的 IANA 时区换算为 UTC；
- 只读取当前订阅来源，并应用当前用户字段覆盖；本地 `busy=false` 会使该 occurrence 不再占用
  时间。

已经完全结束的历史周不新增冲突。来源取消本来就保留过去 occurrence，因此过去事实不会因刷新
重写。

刷新事务先取得账号 `PlanningInputRevision` 写锁，再锁定将要比较的当前 `Plan` 行。计划版本创建
沿用相同的 revision → plan 顺序；因此不会出现“用旧来源创建的新计划”和“冲突记录漏写”同时
提交。

### 3.2 调度签名

只比较影响可安排时间的字段：

- occurrence 身份、起止 UTC 时间；
- 全天/定时语义和 IANA 时区；
- `busy` 与 `scheduled/source_cancelled` 状态；
- 主规则、RDATE、EXDATE、RECURRENCE-ID 移动或取消所形成的实际投影。

名称、说明、地点或解析错误文字变化不单独制造计划冲突。它们仍通过订阅来源版本和规划输入
revision 正常同步；已有本地字段覆盖差异继续由订阅管理页展示。

变化分类：

| 类型 | 含义 |
| --- | --- |
| `added` | 刷新后新增一个占用时间的 occurrence |
| `removed` | 原占用 occurrence 被取消、移除或改为不占用 |
| `moved` | 同一 occurrence 的起止时间或时区变化 |
| `availability_changed` | 其他会改变固定时间可用性的状态变化 |

每项保存用户可读名称、变更前后本地及 UTC 时段、来源事件 ID 和与刷新后区间重叠的当前计划块
ID。只要该周存在调度签名变化，就创建“计划需复核”记录；有重叠块时额外标记为实际重叠。来源
取消即使只释放时间也需复核，但不得显示“发生重叠”。

单周投影超过既有 2000 条上限时，订阅刷新不能因此丢失已经验证的来源快照。该周创建
`details_limited=true` 的保守复核记录，说明来源变化过多、需在日历缩小范围查看；不伪造具体
重叠数量。

## 4. 持久模型

新增 `PlanSourceConflict`：

| 字段 | 语义 |
| --- | --- |
| `id / owner_id` | 稳定 ID 与本人归属 |
| `plan_id / plan_version_id` | 冲突发现时的当前不可变计划版本 |
| `source_id / source_generation` | ICS 来源及成功应用代次 |
| `status` | `open` 或 `resolved` |
| `resolution` | 未处理为 `null`；处理后为 `kept / replanned / superseded` |
| `changes` | 有界 occurrence 变更数组，不保存订阅 URL、UID 或 ICS 正文 |
| `affected_block_ids` | 刷新后实际重叠的计划块 ID 去重数组 |
| `details_limited` | 是否因投影容量只保存保守摘要 |
| `version` | 冲突处理的乐观版本 |
| `detected_at / resolved_at` | 检出和处理时间 |

唯一键为 `(plan_version_id, source_id, source_generation)`。外键同时约束 owner、plan/version 与
source 归属，账号删除级联清理。

同一计划版本和来源的新代次产生冲突时，先把旧的开放记录标为
`resolved/superseded`，再写入新记录；一个来源在同一当前计划上最多有一条开放记录。创建新计划
版本时，把旧当前版本全部开放记录标为 `resolved/replanned`。历史记录不参与当前日历提示，但
进入本人 JSON 导出。

## 5. API 合同

计划读取结果和规划上下文增加：

```json
{
  "source_conflicts": {
    "open_count": 1,
    "overlap_count": 1,
    "items": [
      {
        "id": "uuid",
        "plan_id": "uuid",
        "plan_version_id": "uuid",
        "plan_version": 2,
        "source_id": "uuid",
        "source_name": "学校课表",
        "source_generation": 4,
        "status": "open",
        "resolution": null,
        "changes": [],
        "affected_block_ids": ["uuid"],
        "details_limited": false,
        "version": 1,
        "detected_at": "2026-10-04T02:00:00Z",
        "resolved_at": null
      }
    ]
  }
}
```

`GET /api/v1/planning/blocks` 同时返回范围内当前计划的开放 `source_conflicts`；每个计划块附带
`source_conflict_count`，只统计 `affected_block_ids` 中真实包含该块的记录。

新增：

```text
POST /api/v1/plans/{plan_id}/source-conflicts/resolve
```

请求包含：

```json
{
  "operation_id": "uuid",
  "expected_plan_version": 2,
  "conflict_ids": ["uuid"],
  "resolution": "kept"
}
```

服务端锁定账号 planning revision、计划和所列冲突，要求它们仍属于请求中的当前计划版本且保持
开放。成功后只处理请求列出的 ID；处理期间新到达的冲突不会被误确认。相同操作 ID 和相同内容
返回原结果，不同内容返回幂等冲突。计划版本或冲突版本变化返回 409，并附当前计划版本；跨账号
统一返回 404。

“重新规划”不使用该处理 API。用户显式生成并确认新提案，或手工保存新版本后，旧冲突才以
`replanned` 解决；仅生成尚未确认的提案不会隐藏提示。

## 6. Web 交互

规划页仅在查看当前计划时显示来源冲突区，不覆盖提案预览和历史版本：

- 标题为“订阅来源更新后，当前计划需复核”，明确“第 N 版计划未被自动改动”。
- 按来源展示刷新时间、变化条数、取消/新增/移动摘要和实际重叠块数量。
- 展开项显示变更前后时段；`details_limited` 显示缩小日历范围查看的恢复说明。
- “在日历查看”携带日期、来源和可用的事件 ID，日历打开对应周并定位来源管理。
- “保留当前计划”提交当前可见冲突 ID；失败保留内容和 operation ID，版本冲突后重读。
- “按最新来源重新生成”切到整周当前条件并由用户再次点击或明确触发一次生成；不自动确认、
  不自动扣除第二次以外的额度。AI 冻结时仍可手工调整或保留计划。

统一日历：

- 顶部显示该范围内计划需要复核的来源数量，并提供进入规划页的命令。
- 只有 `affected_block_ids` 命中的计划块使用现有冲突视觉，不把释放时间的复核伪装成重叠。
- 计划块详情说明“订阅来源变化后与此计划块重叠”，仍不提供自动移动或完成任务操作。

布局沿用现有状态带和无嵌套卡片结构；按钮使用 Lucide 图标，桌面、平板、手机和 320px 大字号
下保持可换行且无横向溢出。

## 7. 同步、导出与生命周期

- 冲突创建、处理和新计划版本解决均发出 `entity_type=plan` 的无正文同步事件。`Plan.version`
  只代表计划内容版本，不因提示状态增加；change feed 的序号负责触发跨端刷新。
- 规划页和日历页已订阅 `plan`，收到事件后重新读取服务端状态。
- 本人 JSON 导出在 `planning.source_conflicts` 中包含模型字段和变化摘要；CSV/ICS 不重复输出
  诊断状态。
- 账号注销通过 owner/plan/source 外键级联删除；不得把冲突摘要保留进最小删除回执。
- 历史计划版本保留冲突审计；普通计划读取只突出当前版本开放记录。

## 8. 失败与容量边界

- 订阅抓取失败、304 或无调度变化：不创建、不解决现有冲突。
- 冲突写入失败：来源快照事务整体不提交，worker 保持可恢复租约并重试；不能出现来源已更新但
  提示缺失。
- 用户处理响应未知：复用 operation ID；服务端幂等记录返回同一处理结果。
- 处理时计划已更新：返回 409，UI 重读；新版本创建事务已经把旧提示解决为 `replanned`。
- 来源再次更新：旧开放记录转 `superseded`，只展示最新代次；历史仍可审计。
- 每条记录最多 2000 个变化项和 100 个重叠块 ID；超过时保存 `details_limited` 摘要。单次处理
  最多 100 条开放记录。

## 9. 验证要求

服务端：

- 迁移升级/降级、约束、所有权、唯一代次和级联。
- 已确认计划后订阅新增、移动、取消、busy 变化；区分实际重叠和只需复核。
- 标题/地点变化、304、失败、坏项目保旧、过去 occurrence 不制造冲突。
- 本地 busy 覆盖优先、重复刷新幂等、来源再次变化 supersede、保存新版本 replanned。
- 双 worker、刷新与计划保存并发、解决请求与新刷新并发、未知响应重放。
- change feed、本人导出和账号注销清理。

Web：

- 真实注册、创建任务和计划、创建并刷新受控 ICS 来源、看到当前计划提示。
- 查看新增/移动/取消及重叠说明，从提示进入日历来源。
- 保留计划后跨标签消失；重新生成只有确认新版本后才解决旧提示。
- 刷新失败保留旧计划及旧冲突，不产生新提示。
- 三视口、320px 最大字号深色、键盘、axe、控制台、API 500 和根级横向溢出。
