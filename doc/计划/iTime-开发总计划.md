# iTime 开发总计划

版本：0.1；状态：阶段建议，工期与具体实现范围待需求澄清。

## 1. 原则

先完整访谈和确认可验收范围，再做技术与UI设计；按可验证的业务闭环逐步实现。Web/App用户功能对等是正式交付要求，不能用内部开发分期削减最终范围。原PRD14周尚未包含新增系统，不直接作为承诺。

## 2. 阶段与准入

| 阶段 | 目标 | 主要输出 | 完成标准 |
| --- | --- | --- | --- |
| M0 工程初始化 | 可持续协作与需求输入 | Git、项目凭据入口、文档体系、原PRD和问题清单 | 初始化检查真实通过；远端状态如实记录 |
| M1 需求访谈 | 明确产品和首发范围 | 问题答复、更新PRD、双端矩阵、角色与规则、指标口径 | 冻结首发清单；重大未决项已解决或明确暂缓 |
| M2 架构与交互设计 | 形成可实施方案 | ADR、UI原型、数据/API契约、异常/同步设计、成本评估 | 关键流程和平台差异已确认；测试与需求对应 |
| M3 账号与数据基础 | 真实用户及云数据闭环 | 注册登录、权限、持久化、同步/离线基础、后台入口 | 双端账号、隔离、同步和恢复验证 |
| M4 任务与固定安排 | 获得可靠规划输入 | 任务、重复事件、确认范围内的导入和校对 | 重复/例外/时区/错误样本验证 |
| M5 规划与执行 | 核心价值可用 | 服务端AI、约束校验、调整、版本、专注、困难记录 | 完整计划执行流程；故障与并发路径验证 |
| M6 复盘与优化 | 完整产品闭环 | 复盘会话、报告、建议/记忆、历史与统计 | 跨端接续、事实可修正、建议控制符合规则 |
| M7 运营与商业 | 商业上线所需能力 | 已确认的通知、分享、权益/支付、后台运营 | 故障排查、费用幂等、权限和真实渠道验证 |
| M8 发布验收 | 可交付和维护 | 双端回归、容量、备份恢复、部署、App分发及验收报告 | 已确认验收项有证据；遗留风险明确 |

M3—M7可按垂直业务切片调整顺序，但应尽早验证一条“账号 → 任务 → 规划 → 执行 → 复盘 → 另一端可见”的完整路径。

## 3. 需求访谈轮次建议

1. 产品与平台、是否收费、目标市场、仓库归属。
2. 注册登录、用户数据、AI服务、管理员权限和成本。
3. 固定日程、任务模型、排期算法及异常。
4. 执行、困难、复盘、长期记忆和提醒。
5. 视觉、指标、容量、环境、测试和发布验收。

每轮回答后更新需求、设计及测试，不要求用户重复回答已有明确结论。

## 4. 模块执行计划模板

每模块在开始开发前写明：目标、已确认需求编号、范围、输入输出、前置依赖、设计与技术理由、权限、状态、异常与重试、并发/性能/超时、数据迁移、测试样例、可自动化验收和需要用户验证的体验。

有代码后补实际文件路径与命令。阶段验收须区分已实现、已测试、已联调、已发布，不能合并成笼统“完成”。

## 5. 当前未解依赖

首发平台与业务范围、收费计划、认证方式、管理员访问边界、AI供应商与预算、云环境、设计偏好、期望日期和资源。对应 [访谈清单](../需求/iTime-需求访谈问题清单.md) A、B、C、K、L、O。
